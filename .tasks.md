# Kobold Thin Harness Tasks

## Status Overview

- **Architecture Plan**: Modular Rust monorepo under `crates/`.
- **Target Design**: Thin agent harness decoupling frontends, daemon, kernel, tools, and model backends.
- **Current Phase**: Implementation (TASK-3 ready, TASK-1 & TASK-2 completed).

---

## Tasks

### TASK-1: Workspace Skeleton & `kobold-types` Crate
- **Status**: Completed
- **Scope**:
  - Configure root `Cargo.toml` with workspace members under `crates/*`.
  - Create `crates/kobold-types` crate with zero operational logic and minimal dependencies (`serde`).
  - Define data models in `kobold-types`: `Message`, `Role`, `ToolDefinition`, `ToolCall`, `ToolOutput`, `KernelEvent`.
  - Define trait contracts in `kobold-types`: `Backend` (model inference/streaming), `Tool` (metadata & execution), `EventSink` (event observation), and `ApprovalPolicy` (permission check).
- **Acceptance Criteria**:
  - `cargo check --workspace` compiles cleanly.
  - `crates/kobold-types` has zero network, process, or filesystem I/O dependencies.

### TASK-2: `kobold-context` Conversation & Compaction Crate
- **Status**: Completed
- **Scope**:
  - Create `crates/kobold-context` crate depending on `kobold-types`.
  - Implement conversation message history tracking and deterministic ordering.
  - Implement hybrid token budgeting (reconciling exact provider `Usage` counts with fast ~4 chars/token buffer heuristics).
  - Implement two-tier context compaction:
    1. Prune historical tool outputs to concise provenance reference markers.
    2. Slide intermediate turns when exceeding budget, strictly preserving the system prompt and initial user task.
  - Implement system prompt construction, automatically discovering and injecting `AGENTS.md` (strictly ignoring `CLAUDE.md`).
- **Acceptance Criteria**:
  - Isolated unit tests verifying message history appending, hybrid token reconciliation, tool output pruning, and sliding window.
  - Verification that `AGENTS.md` is discovered and injected into the system prompt while `CLAUDE.md` is ignored.
  - Zero network, process, or filesystem I/O dependencies.

### TASK-3: `kobold-kernel` Agentic Loop & Turn Orchestrator
- **Status**: Ready for Implementation
- **Scope**:
  - Create `crates/kobold-kernel` depending on `kobold-types` and `kobold-context`.
  - Orchestrate turn lifecycle: prompt ingestion, context building, model streaming, sequential tool dispatch, and turn completion.
  - Gate tool execution through `ApprovalPolicy`, emitting approval events and pausing when human authorization is required.
  - Feed tool execution errors back into the conversation context as error results for model self-correction.
  - Stream lifecycle events through the `EventSink` contract.
- **Acceptance Criteria**:
  - Pure async orchestration depending exclusively on `kobold-types` and `kobold-context`.
  - Comprehensive unit tests using mock `Backend`, `Tool`, and `ApprovalPolicy` implementations.

### TASK-4: Execution Tools (`kobold-tool-bash`, `kobold-tool-fs`)
- **Status**: Ready for Implementation
- **Scope**:
  - **`crates/kobold-tool-bash`**:
    - Implement `Tool` trait for a unified `bash` tool (one-shot by default, persistent with `session_id`).
    - Build the macOS `Virtualization.framework` microVM driver with APFS CoW checkpoints (`clonefile`).
    - Build static Rust PID-1 agent in `initramfs` for sub-second guest boot and cgroup v2 execution.
    - Implement host-guest communication over vsock using length-prefixed JSON framing.
    - Implement the quiesced snapshot protocol (`FIFREEZE` / `F_FULLFSYNC` / `clonefile` / `FITHAW`).
    - Implement repository synchronization via `git bundle` (clean host import and branch export).
    - Enforce execution timeouts and bounded output truncation.
  - **`crates/kobold-tool-fs`**:
    - Implement `Tool` trait for structured in-process operations: `read_file` (with line/byte ranges), `write_file`, `edit_file` (search & replace), and `list_dir`.
    - Restrict access to configured workspace root.
- **Acceptance Criteria**:
  - `kobold-tool-bash` boots microVM, runs commands via vsock, and streams output chunks.
  - Checkpoint creation and rewind verified on APFS with sub-second commit latency.
  - Codebase changes exported via `git bundle` to dedicated host branch without modifying host working tree.
  - `kobold-tool-fs` operations execute in-process with zero subprocess overhead.

### TASK-5: OpenAI Backend (`kobold-backend-openai`)
- **Status**: Ready for Implementation
- **Scope**:
  - Create `crates/kobold-backend-openai` implementing the `Backend` trait from `kobold-types`.
  - Implement bidirectional streaming client using the OpenAI Realtime / Responses WebSocket protocol.
  - Manage connection lifecycle with lazy connect upon client typing and a 5-minute idle disconnect timeout.
  - Support `store: true` by default, with dynamic `/zdr on|off` toggle for Zero Data Retention (`store: false`).
  - Stream text and reasoning deltas, tool call chunks, and response completion events as an async `Stream<Item = BackendEvent>`.
  - Support API key authentication and configurable model selection.
- **Acceptance Criteria**:
  - Unit tests verifying WebSocket frame parsing, delta aggregation, and tool call serialization.
  - End-to-end streaming against live or mock WebSocket endpoint.
  - Verified idle disconnect after 5 minutes and reconnection on typing.

### TASK-6: Daemon & Frontends (`kobold-server`, `kobold-client-cli`, `kobold-client-tui`)
- **Status**: Ready for Implementation
- **Scope**:
  - **`crates/kobold-server`**:
    - Headless daemon supervising sessions, assembling kernel, context, tools, and backend.
    - Dual IPC transport: Unix Domain Socket listener and WebSocket listener.
    - Multiplex and broadcast `KernelEvent`s to connected clients.
  - **`crates/kobold-client-cli`**:
    - Fast terminal client connecting to `kobold-server` via UDS, with `/zdr` command and status display.
  - **`crates/kobold-client-tui`**:
    - Interactive Terminal UI built on Ratatui with live streaming, markdown parsing, diff-based approval dialogues, and visible `[ZDR]` status indicator.
- **Acceptance Criteria**:
  - End-to-end execution of a user prompt through client -> server -> kernel -> backend -> tool -> client stream.
  - Dual IPC transports verified with simultaneous local CLI and WebSocket connections.
  - Toggling `/zdr on|off` updates runtime retention and reflects `[ZDR]` indicator in the status line.
